WHAT THIS PAGE IS

Berth is the VRAM leasing service for every GPU you run. Engines ask the berthd node for a lease on the card; the node queues the request, asks the current holder to drain, waits until the driver shows the memory free, and only then grants the berth. Nothing is ever granted on process exit alone, and nothing is claimed as reserved unless the driver measured it. Every stat on this page is collected by the node itself, from the driver, the host, and the engines' own endpoints.

THE TWO MODES

BASIC
the at-a-glance story: the counters, the request KPIs, the tide, the departures board, and the berths. The mode you land on.
ADVANCED
everything a power user wants: full GPU telemetry (clocks, fan, PCIe), host CPU and memory trends, prefill and reingest KPIs, the token ledger, the leaderboard, and the full recent-request table. Toggled in the header, remembered between visits.

THE STATUS WORDS

BOARDING
the request is waiting in the queue for a free berth
DOCKED
the lease is active and the engine is using the card
CASTING OFF
the holder has been asked to drain and is finishing up
ADRIFT
the lease is being released and the memory is on its way out
AGROUND
the release stalled; the memory is not coming back on its own

A magenta CONTESTED flag on a docked row means the driver saw other VRAM holders on the card at grant time, so the measured hold and the free space disagree. The row title and the ticket stamp carry how much they held. CARD RANKING on the engines tab shows how the node orders engines when two at one priority ask for the card inside the juggle window: the config order, or card hours over the last seven days.

THE REQUEST KPIs

DECODE t/s
tokens per second generated across the running engines; the sparkline sums every engine's decode rate over the last hour
PREFILL t/s
prompt tokens processed per second, the engine's intake rate while it reads a request in
TPOT ms
time per output token, the inverse of decode rate, over the last fifteen minutes
P95 ms
the request duration that ninety-five percent of recent requests finished within, last fifteen minutes
P50 ms
the median request duration, last fifteen minutes
REQ/MIN
requests completed per minute over the last five minutes
CACHE %
share of prompt tokens served from the KV cache instead of re-run, last hour
REINGEST %
the complement of cache, the share of prompt tokens that had to be computed from scratch
DRAFT ACCEPT %
of the tokens a speculative draft model proposed, the share the main model accepted, so no work was wasted
PREFILL ms
derived time-to-first-token: uncached prompt tokens divided by the prefill rate, used where the engine does not report it directly
QUEUE
engines waiting in the berth's own queue for a free berth on the card; each engine's own queue - the requests it holds back - is on its card

THE COUNTERS

COLLISIONS AVOIDED
grants that waited for a held card instead of loading on top of the holder
VRAM HANDED OFF
peak measured bytes of every lease whose memory the card then showed as freed
DRAINS
holders asked to give the berth back
AGROUND CAUGHT
stuck releases caught before the card stayed dirty
STOWAWAYS CAUGHT
VRAM holders found on the card with no lease
CONTESTED
grants made while another holder shared the card
REFUSED
requests turned away after their wait expired

Every count is an event the node actually saw. Berth never estimates what might have happened.

CONTEXT AND KV

Context residency draws the engine's own per-request token figures - cached, fresh prefill and generated - as columns against the model's context window, so a request that would not fit its window is visible at a glance; below the columns sit the engines' live KV sessions. The KV pool is each engine's live KV slots (the llama.cpp family's /slots): how many context tokens each session holds against its window, with 75 and 90 percent marks. Stored ranges show the per-minute peak slot fill the harbor folded from the node's samples; the live slots stay live, whatever the range says. An engine without these endpoints reports no window and no slots, and the panels say so rather than guess.

GPU TELEMETRY AND THE MACHINE

The scheduled card reports its power draw against its power limit, temperature, utilisation, and in advanced mode its SM and memory clocks, fan, and PCIe generation and width. A reading of n/a means the driver did not report it, not zero. The machine panel is the host itself: CPU, cores, used and total memory, swap, and the one, five and fifteen minute load averages. Its socket line counts event-stream write timeouts and dropped slow readers, so a stalled log on a live node starts there.

STOWAWAYS AND NO TICKET

A stowaway is any process holding VRAM without a lease. Berth reports it and never kills it. A "no ticket" run is an engine started while the node was down, so it holds the card outside any lease. Both show here read only.
